## C++ style
- **Reference: the Google C++ Style Guide, with deliberate deviations.** Existing code reflects the chosen style; don't flag it as a violation. When something new comes up that the guide has a rule for (first enum, first constant, etc.), point out the guide's recommendation so the user can decide, then record the decision here.
- Chosen so far:
  - Functions and methods are snake_case (`create()`, `get()`), not PascalCase.
  - Types are PascalCase; members have a trailing underscore (`instance_`); non-type template parameters are snake_case like variables (`release_fn`).
  - Namespaces map to directory *subtrees*, but not every directory gets one: add a namespace only to separate things that would collide or be confused. Current set: `mewo` (`core/` except `gpu/`: events, `Match`), `mewo::gpu` (`core/gpu/`: `MoveOnlyHandle`, the `gpu::Instance`/`gpu::Surface`/... aliases, WebGPU string conversion), `mewo::impl` (`impl/` and below: the objects behind C handles, e.g. `impl::Surface`, plus their helpers like `impl::SurfaceSource`). Subdirectories inherit their parent's namespace (`impl/surface/source.hpp` → `mewo::impl`, `core/utility/match.hpp` → `mewo`). No `Impl` suffix on class names.
  - Constants and enumerators use the `k` prefix (`kMaxPasses`, `AdapterRequestFailed::Reason::kUnavailable`).
  - `.cpp` / `.hpp` files, `#pragma once` (not `#define` guards).
  - Include paths always start at `src/` (`"impl/runtime.hpp"`), even for a file's own header; never relative to the current file.
  - Include order (enforced by `.clang-format`): project headers (quoted), then `<mewo/mewo.h>`, then third-party, then the standard library.
  - Every class states its copy/move support explicitly (`= delete` / `= default` / user-defined), even when the compiler would infer it.
  - File-local definitions in a `.cpp` (helpers, constants) go in an unnamed namespace inside `namespace mewo`, closed with `}  // namespace`; not `static`.
  - Constants shared from a header are `inline constexpr` (not needed in a `.cpp`'s unnamed namespace). String constants are `constexpr std::string_view kName = "..."`; convert with `std::string(kName)` where a `std::string` is needed, never via `.data()` (a `string_view` isn't guaranteed NUL-terminated).
  - WebGPU structs are always initialized with their `WGPU_*_INIT` macro, then fields assigned (e.g. `WGPUDeviceDescriptor desc = WGPU_DEVICE_DESCRIPTOR_INIT;`), never `= {}` or bare designated initializers. Remind the user in reviews when one is missed. Why: the macros set non-zero defaults correctly and keep up with header changes.
  - Abbreviations: existing ones are accepted as-is (e.g. `Tex`, `TexView`, `Caps`, `Raii`, `desc`, `cb_info`); don't question them. When the user introduces a *new* abbreviation, point it out (Google's guide says not to abbreviate by deleting letters inside words) so they can decide.
  - Doc comments use `/** ... */` (Javadoc style, matching `mewo.h`), not `//`.
  - Every namespace closes with `}  // namespace name` (`.clang-format`: `FixNamespaceComments`, `ShortNamespaceLines: 0`).
  - Formatting is whatever `.clang-format` (Chromium-based) produces.

## Project vision
- mewo is roughly "Shadertoy, but native": a desktop app for writing and running shaders live.
- Long-term (aspirational, not current scope): run the same engine on the web as a platform.
- Design implication: keep the core portable (WebGPU-style API, platform glue confined to a host layer, no OS calls/blocking/threads assumed in the core), but don't build for the web yet.

## Decisions
_Record each decision with a short "why"._

### Architecture
- **Ghostty-style split (tentative):** a core library, `libmewo`, plus separate frontends in any language (e.g. Swift/SwiftUI on macOS, HTML/CSS on web, something on Windows/Linux). Why: inspired by Ghostty's libghostty + apprt design, and it enforces the core/UI separation the previous version lacked.
- **libmewo exposes a C API and is written against the standard `webgpu.h`** (webgpu-native/webgpu-headers), not a specific implementation's API. The implementation (Dawn, wgpu-native, or emdawnwebgpu for the browser) is picked at build time. Why: one core for native and Wasm; no privileged frontend language.
- **libmewo internals are C++; the public API is pure C** (`mewo.h`). Why: the user knows modern C++ well, so the new territory is the architecture and C API design. Rules: no exceptions or C++ types cross the boundary, opaque handles, explicit ownership.
- **Primary render handoff: the host gives libmewo a native surface** (CAMetalLayer, HWND, Wayland surface, canvas) and libmewo creates its own `WGPUSurface`. A CPU readback path is a possible fallback, and is useful for export and thumbnails anyway.
- **Development happens on both Windows and macOS.** That's why this file lives in the repo: it syncs between machines through git. The core and the reference host must build on both.
- gpui deprioritized: it has no clean way to embed external GPU content (upstream has nothing documented; forks like gpui-ce are experimenting).

### C API object model
- **`mewo_runtime_t`**: process-wide engine. Owns the WebGPU instance/adapter/device/queue, shared caches, and the event queue.
- **`mewo_project_t`**: the document, pure data, **no GPU**. Holds everything that gets saved: metadata, the ordered pass list (name, source, output format/size, named inputs), `main_pass` flag, output pass, shared (Common) source, assets, optional authoring intent (preferred size/aspect), per-pass revision counters.
- **`mewo_session_t`**: one running instance of a project (the user chose "session" over "view"/"player"). Owns everything that exists because the project is being rendered: playback clock, input state, render size, per-pass compiled modules / last-good pipelines / status / diagnostics / output textures / bind groups, uniform buffers, GPU copies of assets, attached surface, frame stats. Never saved. Can run headless (export, thumbnails). Each session has independent simulation state.
- **`mewo_surface_t`**: a native drawing target from the host; a session optionally presents to one.
- A session **reconciles** with its project on each render using the revision counters: recompile edited passes (keep the last good pipeline until the new one compiles), reallocate textures on format/size changes, rebuild bind groups on input changes, rebuild the execution plan on add/remove/reorder.
- **Single-owner create/destroy handles, no refcounting** (`mewo_*_create` / `mewo_*_destroy`, like Ghostty's `ghostty_*_new` / `*_free`). The host destroys children before parents (sessions before their surface/project/runtime, surfaces before their runtime). This is a documented contract only: the core does **not** track live children or assert on wrong destroy order (decided against during step 2 for simplicity: it needs back-pointers and counters in every object, and the contract is spelled out in the `*_destroy` doc comments instead). Why: refcounting was first chosen for GC'd/ARC hosts, but those use explicit disposal (`.delete()`, `Symbol.dispose`) or wrapper classes whose `deinit` frees the handle, and Ghostty ships fine without it; shared ownership, if needed, lives in host wrappers. Escape hatch: adding `mewo_*_add_ref` later and making destroy drop one reference is backward-compatible.
- **Async results come through a pollable event queue** (`mewo_runtime_poll_event`), not callbacks. Why: no reentrancy hazards, and it fits every frontend. An optional `wakeup` callback for hosts that sleep between frames is a maybe, not a promise.
  - **`mewo_runtime_tick` and `mewo_runtime_poll_event` are separate.** `tick` does the work (`wgpuInstanceProcessEvents`, advancing internal state) and produces events; `poll` only pops one. Why: a poll that sometimes does heavy work is surprising, and a drain loop could keep producing events.
  - **`mewo_event_t` is a tagged union** (`type` + named union `variant`) with a `FORCE32` type enum and a reserved byte array that fixes `sizeof`. Why: the host allocates the struct, so adding event types must not change its size (ABI); payloads stay small and details live in queryable state.
  - **Events carry object pointers** (e.g. `session`, NULL for runtime-level). Destroying an object purges its queued events, so hosts never see dangling pointers. Event strings are valid until the next `poll_event` call.
- **Descriptors:** create functions take `const mewo_*_desc_t*` (NULL = all defaults) once they have options; a create with nothing to configure (e.g. `mewo_runtime_create` today) takes no descriptor, and one is added when the first field appears (cheap: hosts link statically). Simple setters/verbs take plain arguments. Booleans in descriptors are named so `false` is the default. There is no project-wide rule for what an enum's zero value means or how it's named (e.g. `MEWO_EVENT_NONE`, `MEWO_SURFACE_SOURCE_NONE`, `MEWO_DEVICE_FAILURE_ERROR` are all `= 0`); decide per enum. Strings are `mewo_string_view_t { data, length }` with a `MEWO_STRLEN` sentinel for NUL-terminated. Descriptors are borrowed for the call; the core copies what it keeps. No `next_in_chain`/size fields: pre-1.0 we add fields freely, and variants use tagged unions. Why: every host links libmewo statically, so header and library can't drift apart, and chaining is Vulkan-scale future-proofing this project doesn't need.
- **Surfaces:** `mewo_surface_desc_t` is a tagged union of native sources (`METAL_LAYER`, `WIN32` (HWND + HINSTANCE), `WAYLAND`, `XLIB`, later `HTML_CANVAS`) plus the initial size in pixels; `impl::Surface::create` (`src/impl/surface.cpp`) translates it into the matching `WGPUSurfaceSource*` chain. The host creates the native object (e.g. SDL: `SDL_Metal_CreateView` + `SDL_Metal_GetLayer`, `SDL_PROP_WINDOW_*` properties; SwiftUI: an `NSView` backed by a `CAMetalLayer`), so the platform `#ifdef`s live in the host and the core never calls AppKit/Win32 (no `.mm` in libmewo). Native handles are borrowed and must outlive the `mewo_surface_t`. The host reports pixel size changes with `mewo_surface_resize` (SDL: `SDL_EVENT_WINDOW_PIXEL_SIZE_CHANGED` + `SDL_GetWindowSizeInPixels`); the core reconfigures lazily at the next render, recovers from `Outdated`/`Lost` itself, and skips presenting at zero size.
- **`impl::Surface` owns its configuration**, not the session: it exposes `acquire(adapter, device)` → `std::optional<gpu::TexView>` (a view of this frame's surface texture; the texture itself stays private to `Surface`, kept alive by the view; nothing = skip this frame), `present()`, and `format()`, with the device/adapter passed per call (no back-pointer to the runtime). `acquire` skips at 0×0; configures when unconfigured or `needs_configure_` (capabilities → format → `wgpuSurfaceConfigure`, freeing caps with `wgpuSurfaceCapabilitiesFreeMembers`); on `SuccessSuboptimal` returns the texture and flags a reconfigure; on `Outdated`/`Lost` flags a reconfigure and skips; on `Timeout` just skips (transient); on `Error` (error surface or failed configure) marks the surface invalid and stops trying. Why: size, format, and reconfigure/recovery are one concern, and because presentation is a blit, the surface format only affects mewo's internal blit pipeline (cached per `format()` in the session), never user pipelines.
- **Surface configuration values:** format = `BGRA8Unorm` if offered, else `RGBA8Unorm`, else `formats[0]`; `presentMode = Fifo` (always supported, vsync, paces the host loop); `alphaMode = Opaque` if offered, else `Auto`; `usage = RenderAttachment`. Why non-sRGB: matches Shadertoy (WebGL's default framebuffer isn't sRGB-encoded, so authors output display values and gamma manually), matches the web (WebGPU canvases only accept `bgra8unorm`/`rgba8unorm`/`rgba16float`), and keeps values unchanged end to end (pass textures → blit → surface). Taking `formats[0]` blindly would make the same shader look different per backend. HDR (`rgba16float`) can be opt-in later.
- **All create functions return `mewo_result_t` and write the handle to an out-param** (e.g. `mewo_session_create(rt, &desc, &out)`). Why: creates must be able to report codes like `NOT_READY`.
- **A session renders a project from day one:** `mewo_session_desc_t` requires a borrowed `project` (must outlive the session). Step 2 uses a stub `mewo_project_create` and a hardcoded shader, so the API shape doesn't change when the model lands. Why: lifetime relationships are real from the start.
- **Surfaces attach via `mewo_session_set_surface(session, surface_or_NULL)`**, not a descriptor field; configuration happens lazily on the next render. The surface is the session's parent: it must outlive the session (or be detached first), per the parent-outlives-child contract (not checked at runtime).
- **The host supplies time:** `mewo_session_render(session, uint64_t host_time_ns)` takes a monotonic timestamp in nanoseconds (`SDL_GetTicksNS`, `performance.now()` × 1e6 on the web). The session owns the playback clock (integer ticks, pause/reset), clamps deltas to >= 0, and derives `mw.time` / `mw.delta_time` from it. Export passes synthetic timestamps (`i * 1'000'000'000 / 60`). Why nanoseconds, not milliseconds: integer ms rounds frame times (16.67 ms becomes 16/17 alternating, ~6% `delta_time` jitter at 60 Hz, ~24% at 240 Hz), while the storage cost is identical; real clock resolution varies (web is coarsened to µs–ms) but the unit is just a container. Large-delta clamping (after sleep/breakpoints) is deferred.
- **Session render size follows its attached surface by default, overridable** (half-res, fixed export size). Presentation is a blit that flips y and scales, so the two sizes can differ at no extra cost.
- **Runtime init sequence:** `mewo_runtime_create` (sync, creates the `WGPUInstance`) → `mewo_surface_create(rt, native_handle)` (sync, `wgpuInstanceCreateSurface`) → `mewo_runtime_request_device(rt, compatible_surface)` (async; adapter then device) → `MEWO_EVENT_DEVICE_READY` / `DEVICE_FAILED`. The compatible surface is **required** (not nullable): hosts create a surface before requesting the device. A headless-only host (export/thumbnails without a window) isn't supported by this signature; revisit if that's needed. Surface *configuration* needs the device, so it happens when a surface is attached to a session. Session creation before `DEVICE_READY` returns `MEWO_ERROR_NOT_READY` (not queued). `DEVICE_LOST` is reported; recovery comes later. Why: only adapter/device requests are async, and passing the surface as `compatibleSurface` picks an adapter that can present to it (matters on dual-GPU laptops); an explicit `request_device` avoids making the first window special or depending on call order.
- **Error handling in the core:** our code never throws. Fallible core functions return an empty result on failure (today `std::optional`; factories return `std::optional<std::unique_ptr<T>>`), and the C API layer maps that to `MEWO_ERROR_INTERNAL`. There is **no internal error type** right now (an `Error` enum + `error_to_result` existed briefly and was deleted as unneeded); reintroduce one (e.g. `std::expected<T, Error>`) when a core function must tell the host *why* it failed with different public codes. `assert` for programmer errors (e.g. null handles). Exceptions stay *enabled* (not `-fno-exceptions`) for now, and the C API layer keeps a `catch (...)` safety net mapping stray throws (`bad_alloc`, third-party) to an internal-error code. Use non-throwing third-party APIs (e.g. nlohmann `parse(..., allow_exceptions=false)`, `find` over `at`). Why: failure is visible in signatures and maps directly onto C result codes; switching to `-fno-exceptions` later (e.g. Wasm size) only touches build flags and the boundary.
- **Core objects that hand `this` to WebGPU callbacks are non-movable** (moves `= delete`d); their factories return `std::optional<std::unique_ptr<T>>` (private constructor, `std::unique_ptr<T>(new T(...))` since `make_unique` can't reach it), and the C handle struct (e.g. `mewo_runtime`) holds the `unique_ptr`. Every WebGPU callback returns immediately on `*_CallbackCancelled` (fired during teardown; touch nothing), copies `WGPUStringView`s into owned strings (`to_string` in `core/gpu/string.hpp`), and is `noexcept` (exceptions must not unwind through Dawn). Why: a callback's `userdata` pointer must stay valid until it fires, and the compiler should enforce that.
- **Where inputs are validated** ("parse, don't validate"):
  - The C API layer (`src/*.cpp`) checks the *C representation*: required pointers → `assert`; enum values that are `NONE`/out of range (a C enum can hold any `int`) and tagged unions missing their data (e.g. null `layer`/`hwnd`) → `MEWO_ERROR_INVALID_ARGUMENT`. It converts C input into C++ types where those states are unrepresentable (e.g. `SurfaceSource` is a `std::variant` with no "none"), via named conversion helpers (e.g. `to_surface_source`) in the file's unnamed namespace.
  - The core checks *domain rules* that would be wrong from any caller (tests, other frontends) inside the owning function (e.g. `create()`), signalling failure through its return type (see error handling above; add an error type once a domain rule needs its own public code).
  - Every C API function has the same shape: assert pointers → convert (invalid → `INVALID_ARGUMENT`) → `try { core call }` → map errors.
  - Zero surface sizes are valid (minimized windows), not an error: the core skips configuring/presenting at 0×0.
- Threading: all calls for a runtime happen on one thread; libmewo does no locking (for now).
- File I/O: libmewo never touches the filesystem. The core owns the project format (parsing/serializing); the host moves the bytes (provides referenced files, writes serialized output, watches files for hot reload).

### Pass model
- A project is an **ordered list of passes**; execution order = list order. Users can add passes before the main pass (Shadertoy-style buffers) and after it (post-processing, e.g. blur). One pass is the **output** (presented/exported; defaults to last). Why: post-processing chains are something Shadertoy lacks; a plain ordered list keeps the core simple and predictable.
- **No special Image pass in the core.** A `main_pass` flag marks the user's main pass for the UI and for Shadertoy import; the core ignores it otherwise. "Pre / main / post" grouping is a UI concept.
- **Inputs bind to sources with an explicit frame:** `current` (only valid from earlier passes) or `previous` (any pass, including itself = feedback). Reordering never silently changes meaning, and `current` edges can't form cycles. Double buffering is inferred (only passes read as `previous`). Any pass may read any earlier pass, e.g. post passes reading pre-image buffers.
- **Invalid states are allowed but reported.** Why: editors need transient invalid states (e.g. mid-reorder). The project exposes validation results (no GPU needed); the UI highlights problems; the session binds a **black fallback texture** for broken inputs (a visible signal) and emits a warning event.
- Other sources: "previous pass in list" (makes post effects reorderable/reusable), image textures, keyboard, later video/audio. Sampling (filter/wrap) is per input binding.
- Per-pass output format (rgba8 / rgba16f / rgba32f) and size (match session, scale, fixed).
- Pass IDs are stable opaque integers from the core, never list indices.
- Common code is a project-level shared source prepended to every pass, not a pass.
- **Named inputs:** each pass input has a user-chosen name used directly in WGSL (e.g. `bloom`). Names default to `in_0`, `in_1`, ... (the UI shows inputs as an ordered list so the numbering reads clearly). Smart defaults derived from the source (e.g. `blur_h`, `noise`) were considered "too magic" for now and may come later; if added, name once at creation and never auto-rename. Names must be valid, unique WGSL identifiers that don't collide with keywords or prelude names. Why: readability, especially in post chains.
- **Feedback state on shader edits (v1):** source edits just swap the pipeline, so buffer contents naturally survive. Format/size changes reallocate that pass's textures (contents reset). An explicit session `reset` clears all buffers and the clock. Deferred: preserving contents across reallocation, and a "reset on compile" option.

### Shader contract
- The contract (entry point, built-ins, input bindings, coordinate conventions) is an API: projects store a **contract version**.
- **WGSL is the only shader language** (browsers only accept WGSL). Shadertoy compatibility is not a goal.
- **Entry point:** the user writes `fn main(fragCoord: vec2f) -> vec4f`. The core owns the vertex shader (fullscreen triangle) and generates the real `@fragment` entry point, which calls the user's `main`. Generated identifiers use a reserved `mewo_` prefix.
- **Inputs in WGSL:** an input named `bloom` is exposed as `bloom_tex` (texture) and `bloom_smp` (sampler). Why: WGSL forbids textures/samplers in structs, so a `bloom.handle`-style struct is impossible; both suffixes abbreviated for consistency. The bare name stays free for user variables, e.g. `let bloom = textureSample(bloom_tex, bloom_smp, uv);`.
- **`mw` fields (v1):** `resolution: vec2f` (this pass's output size), `time: f32` (seconds), `delta_time: f32`, `frame: u32`, `frame_rate: f32`, `mouse: { position: vec2f, click: vec2f, down: bool }`. Mouse is always tracked (including hover), in this pass's pixel space, y-up (stored normalized in the uniform buffer, scaled in generated init). `date` dropped (the core can't read OS clocks; hurts deterministic export). Start minimal: adding fields later is non-breaking, removing is breaking. Possible later: `mouse.buttons`, `mouse.pressed`, `mouse.inside`.
- **Time precision:** WGSL has no `f64`/`u64`/`i64`, so shader-side time stays `f32` seconds (step size ~4 ms at 10 h, ~8 ms at a day; fine for v1). The CPU-side clock is kept as an exact 64-bit integer tick count (or double) and converted to `f32` each frame, so there's no accumulated drift. A precision-friendly split (`u32` whole seconds + `f32` fraction) can be added later if needed.
- **Built-ins are a namespaced struct named `mw` (e.g. `mw.time`, `mw.mouse.down`), not Shadertoy's `iTime`-style globals.** Why: compatibility with Shadertoy isn't a main goal (porting needs work anyway), so there's no reason to carry its baggage (e.g. `vec3` `iResolution`, `iMouse` sign-encoding). Planned approach: the user-facing struct is a `var<private>` filled by generated init code from the underlying uniform buffers (group 0 per-frame, group 1 per-pass), so its layout can be friendly (nested structs, bools) independent of the buffer layout.
- **Shader output is display-referred:** mewo applies no automatic gamma/sRGB encoding anywhere (non-sRGB surface formats, pass textures stored as-is). Shaders that want linear-light math apply gamma themselves, as on Shadertoy.
- **Coordinates are y-up everywhere** (origin bottom-left, like Shadertoy). Internal textures are stored with row 0 = bottom, so `@builtin(position).xy` is already the y-up coordinate and sampling needs no flips. Flip only at presentation to the surface, readback/export, and image asset upload.
- **WGSL extensions/directives (e.g. `f16`) are a project-level setting** that the core emits at the top of the assembled module. Users don't write `enable` directives. Why: directives must precede declarations, and the core can check device support first.
- Module assembly order: user pass source first (so its line numbers need no mapping, since WGSL module-scope declarations are order-independent), then Common source, then generated prelude + entry point. A segment map translates diagnostics (Common lines, collisions with generated names).
- Uniform layout has a single source of truth in C++ (a field table) that generates both the WGSL declarations and the byte offsets.

### Repo & build
- Layout (repo root): `include/mewo/mewo.h` = the public C header hosts include; it includes `include/mewo/detail/*.h`, which split it up for internal organization only (hosts don't include them directly). Every `detail/` header must be included from `mewo.h` so `mewo_c_check` compiles it and clangd can find its flags. `src/` (with its own `CMakeLists.txt`) holds the library: the **C API layer** is `src/<object>.cpp` at the top level (`runtime.cpp`, `surface.cpp`, `version.cpp`; only `extern "C"` functions); `src/impl/<object>.{hpp,cpp}` holds the core object `mewo::impl::<Object>` (`impl::Runtime`, `impl::Surface`, later `impl::Session`, `impl::Project`) **and** its global C handle struct (`struct mewo_runtime { std::unique_ptr<mewo::impl::Runtime> impl; ... };`, defined at global scope because the C header declares it there), with per-object helpers in `src/impl/<object>/` (e.g. `impl/surface/source.hpp`); `src/core/` holds shared internals (`event.*` internal events, `gpu/` = `MoveOnlyHandle` + the `mewo::gpu::*` handle aliases and WebGPU string conversion, `utility/match.hpp`). Tests live in a top-level `tests/` with their own `CMakeLists.txt` (`mewo_tests`, `mewo_c_check`). Also `hosts/` (`sdl/` reference host in plain C, later `macos/`, `web/`; "hosts" because the web isn't really an app), `third_party/`, `cmake/` (`webgpu.cmake` selects the implementation; `utils.cmake` has `mewo_set_target_defaults(target C|CXX)`, which sets the language standard (C11 / C++23, no extensions) and the warning flags). Every first-party target calls `mewo_set_target_defaults`. In CMake, use `${CMAKE_CURRENT_SOURCE_DIR}` / `${PROJECT_SOURCE_DIR}` for include paths, never bare relative paths or `..`.
- **CMake targets:** `mewo` (the whole library, one target; links the JSON lib, webgpu, stb), `mewo_sdl` (links `mewo` + SDL3; only hosts see SDL), and with tests on `mewo_tests` (links `mewo`, white-box: includes `src/` headers directly) and `mewo_c_check`. There is **no separate `mewo_model` target** anymore (dropped during step 2): the project/shader model code staying GPU-free (never including webgpu) is a convention checked in review, not enforced by the build. Why: one target is simpler, and the split forced awkward placement questions (e.g. where `Error` lives); the cost is that tests now need Dawn built, which is a one-time cost per build directory.
- The top-level `src/*.cpp` files are the only place C functions meet C++ (thin `extern "C"` + try/catch forwarding). WebGPU-implementation-specific code (surface sources, extensions) stays inside the `impl/` files that need it.
- `tests/c_check.c` (target `mewo_c_check`, an OBJECT library) compiles `mewo.h` as C11 `-pedantic` to catch C++-isms. It must stay C11, not C23: C23 makes `f()` mean `f(void)` and makes `bool` a keyword, which would hide exactly the mistakes it exists to catch.
- **Presets** (`CMakePresets.json`): configure `debug-clang` / `release-clang` (Ninja, clang/clang++, `build/<preset>`, compile_commands on). Build presets per configuration: `<cfg>` (everything), `<cfg>-tests` (`mewo_tests` + `mewo_c_check`), `<cfg>-host-sdl` (`mewo_sdl`). Test presets per configuration with `outputOnFailure` and `noTestsAction: error`. The user drives builds through VS Code's CMake Tools extension ("CMake: Select Build Preset"; "[Targets In Preset]" is the target setting, not the preset).
- **Gotchas found during setup:** Dawn registers `tint_unittests` with CTest unless `TINT_BUILD_TESTS` is OFF. After adding any `set(... CACHE ...)` dependency option to an existing build dir, reconfigure with `cmake --preset <p> --fresh`, because non-`FORCE` cache sets don't override cached values. Multi-line generator expressions break (whitespace splits or leaks into flags); use one-line `"$<...:a;b>"` forms.
- **Dawn first** as the `webgpu.h` implementation, selected through `cmake/webgpu.cmake` so wgpu-native can be added later.
- **Dependencies are git submodules only** (no FetchContent). Small single-header deps (stb_image) are vendored in `third_party/`. Note: Dawn's own build may still fetch its dependencies via its script (`DAWN_FETCH_DEPENDENCIES`).
- **Tests use Catch2 v3** (submodule, registered with CTest via `catch_discover_tests`). Why: expression-decomposing `REQUIRE`, and `SECTION`s suit the many small variations in GPU-free project/shader model tests; v3 is a compiled library, so no single-header compile cost.
- The macOS SwiftUI app will be an Xcode/SwiftPM project linking a libmewo static lib/xcframework, not built by CMake.

### Dev environment
- **Windows:** LLVM via winget (`LLVM.LLVM`), but winget doesn't add `C:\Program Files\LLVM\bin` to PATH; add it manually. CMake (`Kitware.CMake`) and Ninja (`Ninja-build.Ninja`) via winget. Clang targets the MSVC ABI, so it needs **Build Tools for Visual Studio 2026** (winget id `Microsoft.VisualStudio.BuildTools`, no year in the id) with the `Microsoft.VisualStudio.Workload.VCTools` workload + recommended components (MSVC toolset and Windows SDK). Use the GNU-style `clang`/`clang++` drivers, not `clang-cl`, to match the warning flags.
- **macOS:** Apple Clang (its libc++ lags upstream LLVM on C++23 features). Clone with `--recursive` or run `git submodule update --init`. Dawn's dependency fetch needs Python 3 on both machines.

## Roadmap
1. Skeleton: CMake targets, presets, submodules, placeholder sources; `mewo_sdl` prints `mewo_get_version()` and one Catch2 test passes, on both machines.
2. First vertical slice: `mewo_runtime_t` with async device init reported via the event queue, `mewo_surface_t` from SDL's native window handle (`gpu/` seam), a minimal session drawing one hardcoded shader, and the SDL host on SDL3 main callbacks (`SDL_AppInit`/`SDL_AppIterate`/...).
3. Real project model: project data model, validation, shader assembly + segment map (in `src/impl/project.*` and related files, GPU-free by convention). Test-driven with the `<cfg>-tests` presets.
4. Sessions render real projects: single pass, then multi-pass with feedback.
