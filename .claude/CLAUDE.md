## C++ style
- **Reference: the Google C++ Style Guide, with deliberate deviations.** Existing code reflects the chosen style; don't flag it as a violation. When something new comes up that the guide has a rule for (first enum, first constant, etc.), point out the guide's recommendation so the user can decide, then record the decision here.
- Chosen so far:
  - Functions and methods are snake_case (`create()`, `get()`), not PascalCase.
  - Types are PascalCase; members have a trailing underscore (`instance_`); non-type template parameters are snake_case like variables (`release_fn`).
  - Namespaces map to directory *subtrees*, but not every directory gets one: add a namespace only to separate things that would collide or be confused. Current set: `mewo` (`core/` except `gpu/`: events, `Match`, `Pass`), `mewo::gpu` (`core/gpu/`: `MoveOnlyHandle`, the `gpu::Instance`/`gpu::Surface`/... aliases, WebGPU string conversion), `mewo::impl` (`impl/` and below: the objects behind C handles, e.g. `impl::Surface`, plus their helpers like `impl::SurfaceSource`). Subdirectories inherit their parent's namespace (`impl/surface/source.hpp` → `mewo::impl`, `core/utility/match.hpp` → `mewo`). No `Impl` suffix on class names.
  - Constants and enumerators use the `k` prefix (`kMaxPasses`, `AdapterRequestFailed::Reason::kUnavailable`).
  - `.cpp` / `.hpp` files, `#pragma once` (not `#define` guards).
  - Include paths always start at `src/` (`"impl/runtime.hpp"`), even for a file's own header; never relative to the current file.
  - Include order (enforced by `.clang-format`): project headers (quoted), then `<mewo/mewo.h>`, then third-party, then the standard library.
  - Every class states its copy/move support explicitly (`= delete` / `= default` / user-defined), even when the compiler would infer it. Exception (a deliberate deviation from Google's guide, which wants the four declarations in each class): classes that are neither copyable nor movable inherit `private mewo::Pinned` (`core/pinned.hpp`) instead of spelling out four `= delete`s. Movable/copyable classes still write their `= default`s.
  - File-local definitions in a `.cpp` (helpers, constants) go in an unnamed namespace inside `namespace mewo`, closed with `}  // namespace`; not `static`.
  - Constants shared from a header are `inline constexpr` (not needed in a `.cpp`'s unnamed namespace). String constants are `constexpr std::string_view kName = "..."`; convert with `std::string(kName)` where a `std::string` is needed, never via `.data()` (a `string_view` isn't guaranteed NUL-terminated).
  - WebGPU structs are always initialized with their `WGPU_*_INIT` macro, then fields assigned (e.g. `WGPUDeviceDescriptor desc = WGPU_DEVICE_DESCRIPTOR_INIT;`), never `= {}` or bare designated initializers. Remind the user in reviews when one is missed. Why: the macros set non-zero defaults correctly and keep up with header changes.
  - Abbreviations: existing ones are accepted as-is (e.g. `Tex`, `TexView`, `Caps`, `Raii`, `Cmd` (`CmdEncoder`, `CmdBuf`), `desc`, `cb_info`, `idx` / `Idx` (`pass_idx`, `kIdxA`), `LineNum` (matches WebGPU's `lineNum`), `LineCol`); don't question them. When the user introduces a *new* abbreviation, point it out (Google's guide says not to abbreviate by deleting letters inside words) so they can decide.
  - Single-statement `if`/loop bodies may omit braces (used throughout the codebase); don't flag them.
  - Doc comments use `/** ... */` (Javadoc style, matching `mewo.h`), not `//`.
  - Every namespace closes with `}  // namespace name` (`.clang-format`: `FixNamespaceComments`, `ShortNamespaceLines: 0`).
  - Formatting is whatever `.clang-format` (Chromium-based) produces.

## Project vision
- mewo is roughly "Shadertoy, but native": a desktop app for writing and running shaders live.
- Run the same engine on the web as a platform. Under the leaning frontend plan (see "Frontend plan" under Architecture) the Wasm build also becomes the shipping path on Windows/Linux, so it moves from aspirational to a planned slice after step 11 (step 15).
- Design implication: keep the core portable (WebGPU-style API, platform glue confined to a host layer, no OS calls/blocking/threads assumed in the core). Don't do web-specific work before step 15.

## Prior art
- Branch `senior-project` holds the previous version (school senior design project): C++23, Dawn/WebGPU, WGSL, SDL3, Dear ImGui. **Reference only; don't reuse its code.**
- Lessons from it: the UI owned core concerns (shader prelude in `Editor`, `Project` depended on `Editor`); the model was single-pass with no passes/channels; one god event variant + god class; blocking shader compilation (`WaitAny`) wouldn't work on the web; time/frame counters were tangled with gfx and ImGui; the uniform layout was duplicated by hand between C++ and the WGSL prelude.

## Decisions
_Record each decision with a short "why"._

### Architecture
- **Ghostty-style split (tentative):** a core library, `libmewo`, plus separate frontends in any language (e.g. Swift/SwiftUI on macOS, HTML/CSS on web, something on Windows/Linux). Why: inspired by Ghostty's libghostty + apprt design, and it enforces the core/UI separation the previous version lacked.
- **Frontend plan (leaning strongly, very likely but not final):** two frontends.
  1. **HTML/TS frontend for Windows, Linux, and the web:** libmewo compiled to Wasm (emdawnwebgpu), rendering into a `<canvas>` on the browser's WebGPU through an `HTML_CANVAS` surface source. Shipped in Electron on Windows/Linux (Electron route B under Open questions) and as a web page in browsers (some features, like folder access, may be Chromium-only via the File System Access API). Electron adds `fs` access/watching and native menus; the page itself is the same.
  2. **Native Swift frontend on Apple platforms** (AppKit and/or UIKit, or SwiftUI with `NSViewRepresentable`/`UIViewRepresentable`; not settled): a `CAMetalLayer`-backed view through the existing `METAL_LAYER` source, libmewo linked as a native static lib (Dawn/Metal).
  - Why: two frontends cover four targets; the HTML canvas lets UI draw over the render with no copy or overlay problems, and it doubles as the web platform from the vision; the Apple side keeps native feel and the zero-copy surface path. Native toolkits elsewhere meant one frontend per OS, and toolkits that only composite their own `wgpu` textures (gpui etc.) don't fit (see Open questions).
  - **Linux means Wayland only; X11 is not supported** (user decision, 2026-11). Why: Chromium's Linux WebGPU support and the reports of it working center on Wayland, and supporting one display server halves the testing matrix. The Electron app should run under Ozone/Wayland (force it with `--ozone-platform=wayland` if the Electron version doesn't pick it automatically).
  - Consequences: native Windows/Linux libmewo builds become dev/test only (SDL host, tests; the fast debugging loop, keep them). Two library build pipelines (native static lib for Apple, Wasm). File access stays host-side (already a rule).
  - To verify before committing: WebGPU availability in Electron on Linux (researched 2026-11: Chrome enabled Linux WebGPU through a gradual rollout, Intel Gen12+ first in 144, NVIDIA later around 147; it runs Dawn on Vulkan while the rest of Chromium stays on GL. Electron doesn't get Chrome's staged rollouts and has had Vulkan off by default (electron#40929), so expect to set `enable-unsafe-webgpu` / `enable-features=Vulkan` switches from the main process; AMD status unclear; test on real hardware); Dawn's iOS support if UIKit/iOS is wanted.
  - **emdawnwebgpu without Asyncify (checked in Dawn's source 2026-11, confirm at runtime in 15.3):** its `EventManager` marks `AllowProcessEvents` futures ready when the browser promise resolves, and `wgpuInstanceProcessEvents` fires the ready ones without blocking or Asyncify (only `WaitAny` with a timeout > 0 needs Asyncify/JSPI). All of mewo's callbacks already use `AllowProcessEvents`, so `mewo_runtime_tick` works unchanged, provided the host returns to the browser event loop between ticks (rAF loop, never a busy-wait), because promises only resolve there. Never use `wgpuInstanceWaitAny` with a timeout in the core.
  - The SDL reference host stays regardless.
- **libmewo exposes a C API and is written against the standard `webgpu.h`** (webgpu-native/webgpu-headers), not a specific implementation's API. The implementation (Dawn, wgpu-native, or emdawnwebgpu for the browser) is picked at build time. Why: one core for native and Wasm; no privileged frontend language.
- **libmewo internals are C++; the public API is pure C** (`mewo.h`). Why: the user knows modern C++ well, so the new territory is the architecture and C API design. Rules: no exceptions or C++ types cross the boundary, opaque handles, explicit ownership.
- **Primary render handoff: the host gives libmewo a native surface** (CAMetalLayer, HWND, Wayland surface, canvas) and libmewo creates its own `WGPUSurface`. A CPU readback path is a possible fallback, and is useful for export and thumbnails anyway.
- **Development happens on both Windows and macOS.** That's why this file lives in the repo: it syncs between machines through git. The core and the reference host must build on both.
- gpui deprioritized: it has no clean way to embed external GPU content. Rechecked 2026-11: upstream Zed gpui's `surface()` only takes NV12 `CVPixelBuffer`s on macOS and does nothing on Windows/wgpu (proposals in discussions, nothing merged). The gpui-ce fork merged a custom-GPU API (#237: shared *Rust `wgpu`* device/queue + offscreen render target composited via `surface()`), but it requires gpui-ce's wgpu renderer (opt-in on macOS via #287; Windows wgpu renderer + custom-GPU surfaces in PR #313, still open as of 2026-11-05; upstream Zed has a proposal for externally owned D3D11 SRVs in `surface()`, discussion #64849, no maintainer response or PR yet). Mismatch with mewo: libmewo has its own Dawn device behind `webgpu.h`, so it can't render on gpui's Rust `wgpu::Device`; using gpui would need a new handoff (cross-API shared textures, e.g. Dawn SharedTextureMemory with IOSurface/DXGI handles), CPU readback, or a native child view overlaid on a placeholder element.

### C API object model
- **`mewo_runtime_t`**: process-wide engine. Owns the WebGPU instance/adapter/device/queue, shared caches, and the event queue.
- **`mewo_project_t`**: the document, pure data, **no GPU**. Holds everything that gets saved: metadata, the ordered pass list (name, source, named external inputs; at least one pass), shared (Common) source, assets, optional authoring intent (preferred size/aspect), per-pass revision counters.
- **`mewo_session_t`**: one running instance of a project (the user chose "session" over "view"/"player"). Owns everything that exists because the project is being rendered: playback clock, input state, render size, per-pass compiled modules / last-good pipelines / status / diagnostics / bind groups, the two ping-pong pass textures, uniform buffers, GPU copies of assets, frame stats. Never saved. Can run headless (export, thumbnails). Each session has independent simulation state.
- **`mewo_surface_t`**: a native drawing target from the host; a session optionally presents to one.
- A session **reconciles** with its project on each render using the revision counters: recompile edited passes (keep the last good pipeline until the new one compiles), reallocate textures on render size changes, rebuild bind groups on input changes, rebuild the execution plan on add/remove/reorder.
- **Single-owner create/destroy handles, no refcounting** (`mewo_*_create` / `mewo_*_destroy`, like Ghostty's `ghostty_*_new` / `*_free`). The host destroys children before parents (sessions before their project/runtime, surfaces before their runtime; sessions don't hold surfaces, so there's no session↔surface ordering). This is a documented contract only: the core does **not** track live children or assert on wrong destroy order (decided against during step 2 for simplicity: it needs back-pointers and counters in every object, and the contract is spelled out in the `*_destroy` doc comments instead). Why: refcounting was first chosen for GC'd/ARC hosts, but those use explicit disposal (`.delete()`, `Symbol.dispose`) or wrapper classes whose `deinit` frees the handle, and Ghostty ships fine without it; shared ownership, if needed, lives in host wrappers. Escape hatch: adding `mewo_*_add_ref` later and making destroy drop one reference is backward-compatible.
- **Runtime-level async results come through a pollable event queue** (`mewo_runtime_poll_event`), not callbacks. Why: no reentrancy hazards, and it fits every frontend. An optional `wakeup` callback for hosts that sleep between frames is a maybe, not a promise.
  - **`mewo_runtime_tick` and `mewo_runtime_poll_event` are separate.** `tick` does the work (`wgpuInstanceProcessEvents`, advancing internal state) and produces events; `poll` only pops one. Why: a poll that sometimes does heavy work is surprising, and a drain loop could keep producing events.
  - **`mewo_event_t` is a tagged union** (`type` + named union `variant`) with a `*_FORCE_INT` (`MEWO_ENUM_FORCE_INT`) sentinel on every enum and a reserved byte array that fixes `sizeof`. Why: the host allocates the struct, so adding event types must not change its size (ABI); payloads stay small and details live in queryable state.
  - **Events are runtime-level only and carry no object pointers.** Event strings are valid until the next `poll_event` call. Session-level async results (compile status, later diagnostics) are **pull-based state plus a change counter**, not events (decided in step 5): the session stores each pass's latest status, bumps a session-wide **pass status revision** (`mewo_session_get_pass_status_revision`) when any status changes, and the host compares one integer per frame and re-reads details only when it moved. Why: UIs display state, not history, so with events every host would fold the stream back into state; a revision can't overflow, frames skipped while hidden lose nothing, and nothing needs purging when a session is destroyed. The alternatives were rejected: session events on the runtime queue need a session pointer, a handle back-pointer in `impl::Session`, and purge-on-destroy; per-session queues were sound but a whole queue for one event type. If a per-object event is ever truly needed (e.g. a host must see every individual occurrence), poll it from the owning object so the C layer can fill the pointer from its argument, rather than reviving pointers + purge.
- **Descriptors:** create functions take `const mewo_*_descriptor_t*` (NULL = all defaults) once they have options; a create with nothing to configure (e.g. `mewo_runtime_create` today) takes no descriptor, and one is added when the first field appears (cheap: hosts link statically). Simple setters/verbs take plain arguments. Booleans in descriptors are named so `false` is the default. There is no project-wide rule for what an enum's zero value means or how it's named (e.g. `MEWO_EVENT_NONE`, `MEWO_SURFACE_SOURCE_NONE`, `MEWO_DEVICE_FAILURE_ERROR` are all `= 0`); decide per enum. Strings are `mewo_string_view_t { data, length }` with a `MEWO_STRING_VIEW_SENTINEL` length for NUL-terminated. Descriptors are borrowed for the call; the core copies what it keeps. No `next_in_chain`/size fields: pre-1.0 we add fields freely, and variants use tagged unions. Why: every host links libmewo statically, so header and library can't drift apart, and chaining is Vulkan-scale future-proofing this project doesn't need.
- **Surfaces:** `mewo_surface_descriptor_t` is a tagged union of native sources (`METAL_LAYER`, `WIN32` (HWND + HINSTANCE), later `WAYLAND` (if the SDL dev host is ever run on Linux) and `HTML_CANVAS`; no `XLIB`/XCB, since X11 isn't supported) plus the initial size in pixels; `impl::Surface::create` (`src/impl/surface.cpp`) translates it into the matching `WGPUSurfaceSource*` chain. The host creates the native object (e.g. SDL: `SDL_Metal_CreateView` + `SDL_Metal_GetLayer`, `SDL_PROP_WINDOW_*` properties; SwiftUI: an `NSView` backed by a `CAMetalLayer`), so the platform `#ifdef`s live in the host and the core never calls AppKit/Win32 (no `.mm` in libmewo). Native handles are borrowed and must outlive the `mewo_surface_t`. The host reports pixel size changes with `mewo_surface_resize` (SDL: `SDL_EVENT_WINDOW_PIXEL_SIZE_CHANGED` + `SDL_GetWindowSizeInPixels`); the core reconfigures lazily at the next render, recovers from `Outdated`/`Lost` itself, and skips presenting at zero size.
- **`impl::Surface` owns its configuration**, not the session: it exposes `acquire(adapter, device)` → `std::optional<gpu::TexView>` (a view of this frame's surface texture; the texture itself stays private to `Surface`, kept alive by the view; nothing = skip this frame), `present()`, and `format()`, with the device/adapter passed per call (no back-pointer to the runtime). `acquire` skips at 0×0; configures when unconfigured or `needs_configure_` (capabilities → format → `wgpuSurfaceConfigure`, freeing caps with `wgpuSurfaceCapabilitiesFreeMembers`); on `SuccessSuboptimal` returns the texture and flags a reconfigure; on `Outdated`/`Lost` flags a reconfigure and skips; on `Timeout` just skips (transient); on `Error` (error surface or failed configure) marks the surface invalid and stops trying. Why: size, format, and reconfigure/recovery are one concern, and because presentation is a blit, the surface format only affects mewo's internal blit pipeline (cached per `format()` in the session), never user pipelines.
- **Surface configuration values:** format = `BGRA8Unorm` if offered, else `RGBA8Unorm`, else `formats[0]`; `presentMode = Fifo` (always supported, vsync, paces the host loop); `alphaMode = Opaque` if offered, else `Auto`; `usage = RenderAttachment`. Why non-sRGB: matches Shadertoy (WebGL's default framebuffer isn't sRGB-encoded, so authors output display values and gamma manually), matches the web (WebGPU canvases only accept `bgra8unorm`/`rgba8unorm`/`rgba16float`), and keeps values unchanged end to end (pass textures → blit → surface). Taking `formats[0]` blindly would make the same shader look different per backend. HDR (`rgba16float`) can be opt-in later.
- **All create functions return `mewo_result_t` and write the handle to an out-param** (e.g. `mewo_session_create(rt, &desc, &out)`). Why: creates must be able to report codes like `NOT_READY`.
- **A session renders a project from day one:** `mewo_session_descriptor_t` requires a borrowed `project` (must outlive the session). Step 2 uses a stub `mewo_project_create` and a hardcoded shader, so the API shape doesn't change when the model lands. Why: lifetime relationships are real from the start.
- **The surface is passed per render call, not attached:** `mewo_session_render(session, surface_or_NULL, host_time_ns)`; `NULL` = headless (render without presenting). The session stores no surface pointer, and there is no `set_surface`/detach. The surface only needs to be alive during the call, so hosts can destroy or switch surfaces freely between frames. Surface *configuration* still happens lazily inside `impl::Surface::acquire`. Why: with explicit render sizes (below), the session only needed the surface to present, and storing it created a session→surface lifetime contract that nothing checks; passing it per call removes that whole class of misuse, matching how `acquire(adapter, device)` takes its dependencies per call. Rendering one session to two surfaces in a frame re-renders (the second call sees a zero time delta); a "render once, present to many" path can come later.
- **The host supplies time:** `mewo_session_render(session, surface_or_NULL, uint64_t host_time_ns)` takes a monotonic timestamp in nanoseconds (`SDL_GetTicksNS`, `performance.now()` × 1e6 on the web). The session owns the playback clock (integer ticks, pause/reset), clamps deltas to >= 0, and derives `mw.time` / `mw.delta_time` from it. Export passes synthetic timestamps (`i * 1'000'000'000 / 60`). Why nanoseconds, not milliseconds: integer ms rounds frame times (16.67 ms becomes 16/17 alternating, ~6% `delta_time` jitter at 60 Hz, ~24% at 240 Hz), while the storage cost is identical; real clock resolution varies (web is coarsened to µs–ms) but the unit is just a container. Large-delta clamping (after sleep/breakpoints) is deferred.
- **A session always has an explicit, non-zero render size, set by the host** (option A, chosen in step 2). `mewo_session_descriptor_t.render_width/height` are required and non-zero (0 → `MEWO_ERROR_INVALID_ARGUMENT`); `mewo_session_set_render_size(session, w, h)` changes it (also non-zero). The session never derives its size from the surface, so `impl::Session` holds a plain `Dimensions` (no optional, no "no size" state). The host owns two independent sizes: the **surface size** (window pixels, always reported via `mewo_surface_resize`) and the **render size** (`mw.resolution`, the host's choice: follow the window by setting it on every resize, fixed for export, half-res, tiny for pixel art; skip the call on a 0×0 minimize so the last size (and, once feedback exists, its buffers) survives). Presentation is a blit that flips y and stretches the render size to the surface size (no aspect preservation for now; fit/letterbox can become an option later, since it only touches the blit). Why: the earlier "follow the attached surface by default" rule created an invalid state (no fixed size and no surface → no size) between `create` and `set_surface`, after detaching, and for headless sessions; making the size explicit removes it, keeps the core simple (the host already handles resize events, like it supplies time), and keeps sizes stable while minimized.
- **Runtime init sequence:** `mewo_runtime_create` (sync, creates the `WGPUInstance`) → `mewo_surface_create(rt, native_handle)` (sync, `wgpuInstanceCreateSurface`) → `mewo_runtime_request_device(rt, compatible_surface_or_NULL)` (async; adapter then device) → `MEWO_EVENT_DEVICE_READY` / `DEVICE_FAILED`. The compatible surface is **optional**: windowed hosts pass their surface (so the adapter can present to it); headless hosts (export, thumbnails, tests with no window) pass NULL. Briefly made required during step 2, then reverted because headless is a supported use case. With NULL, a surface created later could in rare cases be incompatible with the chosen adapter; that shows up as `wgpuSurfaceGetCapabilities` failing, which `impl::Surface` already treats as an invalid surface. Surface *configuration* needs the device, so it happens lazily on the first `mewo_session_render` that targets the surface. Session creation before `DEVICE_READY` returns `MEWO_ERROR_NOT_READY` (not queued). `DEVICE_LOST` is reported; recovery comes later. Why: only adapter/device requests are async, and passing the surface as `compatibleSurface` picks an adapter that can present to it (matters on dual-GPU laptops); an explicit `request_device` avoids making the first window special or depending on call order.
- **Error handling in the core:** our code never throws. Fallible core functions return an empty result on failure (today `std::optional`; factories return `std::optional<std::unique_ptr<T>>`), and the C API layer maps that to `MEWO_ERROR_INTERNAL`. There is **no internal error type** right now (an `Error` enum + `error_to_result` existed briefly and was deleted as unneeded); reintroduce one (e.g. `std::expected<T, Error>`) when a core function must tell the host *why* it failed with different public codes. `assert` for programmer errors (e.g. null handles). Exceptions stay *enabled* (not `-fno-exceptions`) for now, and the C API layer keeps a `catch (...)` safety net mapping stray throws (`bad_alloc`, third-party) to an internal-error code. Use non-throwing third-party APIs (e.g. nlohmann `parse(..., allow_exceptions=false)`, `find` over `at`). Why: failure is visible in signatures and maps directly onto C result codes; switching to `-fno-exceptions` later (e.g. Wasm size) only touches build flags and the boundary.
- **Core objects that hand `this` to WebGPU callbacks, or that others hold references to, are non-movable** (`private Pinned`); the same applies to other C handle objects (`impl::Project`, `impl::Surface`) for consistency, and since they live behind `unique_ptr` it costs nothing. A pinned type can't be stored directly in a `std::vector` (it needs moves); use `std::vector<std::unique_ptr<T>>`. their factories return `std::optional<std::unique_ptr<T>>` (private constructor, `std::unique_ptr<T>(new T(...))` since `make_unique` can't reach it), and the C handle struct (e.g. `mewo_runtime`) holds the `unique_ptr`. Every WebGPU callback returns immediately on `*_CallbackCancelled` (fired during teardown; touch nothing), copies `WGPUStringView`s into owned strings (`to_string` in `core/gpu/string.hpp`), and is `noexcept` (exceptions must not unwind through Dawn). Why: a callback's `userdata` pointer must stay valid until it fires, and the compiler should enforce that.
- **Async pipeline compiles go through a runtime-owned inbox keyed by integer tickets** (decided in step 4). `Runtime::start_compile_request` calls `wgpuDeviceCreateRenderPipelineAsync` with `userdata1 = Runtime*` and `userdata2` = a `uint32_t` `CompileRequestId` cast through `uintptr_t` (32-bit so it fits on wasm32; never a pointer, so nothing dangles). The callbacks only write into the ticket's `CompileEntry` in the runtime's map (pipeline result + compilation messages + the request's `SegmentMap`; see "Compile diagnostics"); `PassState` holds its pending ID, takes the entry with `take_compile_request` at the start of `render` once both halves arrived, and keeps drawing its last good pipeline on failure (with no pipeline yet, the pass is skipped and its target stays cleared black). A pending ID is discarded when a newer compile for that pass starts and in `~Session`: `discard_compile_request` erases the entry, and a late callback finds no entry and returns (owned handles release themselves). Why: `CallbackCancelled` only fires when the device/instance is torn down, not when a session is destroyed, so any userdata pointing into a session (or a `PassState`, which moves inside a vector) could dangle; the runtime outlives every session, so it's the only safe target, and the ticket design needs no per-compile heap object.
- **Which C API functions need `try`/`catch`:** exactly those whose call path can throw a C++ exception (in practice: anything that allocates: `new`, `std::string`, containers, `unique_ptr` construction), because an exception escaping an `extern "C"` function unwinds into the host's frames (undefined behavior). WebGPU calls don't throw and our callbacks are `noexcept`. Functions returning `mewo_result_t` map a caught exception to `MEWO_ERROR_INTERNAL`; others pick a safe fallback and wrap only the line that can throw (e.g. `mewo_runtime_poll_event` catches just the message copy and delivers the event with an empty message, since the event type and payload can't fail; it keeps returning `bool` because "queue empty" isn't an error and OOM has no useful host-side recovery). Current status: creates (wrapped), destroys / `tick` / `request_device` / `surface_resize` / `get_version` / the pass status and diagnostic getters (can't throw, no wrapper needed; `mewo_session_destroy` discards pending compile tickets, which only erases from a map), `mewo_project_add_pass` (copies strings, wrapped), `mewo_project_remove_pass` / `move_pass` (only move passes, no wrapper), `mewo_runtime_poll_event` (copies a `std::string`, **needs the message-copy catch**), `mewo_session_render` (will allocate, needs one; reason it returns `mewo_result_t`). Check every new C API function against this rule in reviews.
- **Compile diagnostics** (decided in step 8): the core's `Diagnostic` (`core/compilation/diagnostic.hpp`) is severity + owned message + `std::optional<Location>` (a `RelativeLine` from the segment map plus a 1-based column in UTF-8 bytes). Runtime compile tickets carry both async halves (pipeline result + `wgpuShaderModuleGetCompilationInfo` messages) and the request's `SegmentMap`; an entry is taken only when both halves arrived, and discard always erases (late callbacks find nothing; owned handles release themselves). `PassState` translates messages once on arrival. If the pipeline failed but no message has error severity (e.g. a layout mismatch with valid WGSL), the pipeline's message becomes one location-less error, so a failed compile always has at least one error diagnostic. Unknown WebGPU message types map to error (never `unreachable`: it's external data). `wgpuDeviceCreateShaderModule` is wrapped in a `Validation` error scope whose pop callback discards the error: a broken shader would otherwise also reach the uncaptured-error callback (a duplicate `GPU_ERROR` event). Keep the scope tight around module creation so real validation errors elsewhere still surface; pipeline-async failures never reach the uncaptured callback anyway.
  - **Diagnostics live outside the status variant** (`PassState::diagnostics_`, "from the last completed compile") and are replaced only when a new result arrives, so they survive `Pending`. Why: editors recompile on every edit, and clearing on each request would make error markers flicker. The session's pass status revision already bumps when a result arrives, so it also signals diagnostic changes.
  - **C shape:** `mewo_diagnostic_t` { severity, message, source, line, column }. "No position" is `source = NONE` (= 0) rather than a separate bool (like `MEWO_PASS_ID_NONE`: zeroed reads as none, nothing can disagree). Public source names are `PASS` / `COMMON` / `GENERATED` ("prelude" is an internal word). Access is count + get-by-index per pass on the session (`INVALID_ARGUMENT` for unknown pass IDs or out-of-range indices), matching `mewo_project_get_pass_count`/`get_pass_id`. Strings are valid until the next `mewo_session_render` (they view `PassState`'s strings, which only change inside `render`). The getters don't allocate, so no `try`/`catch`. `mewo_pass_compile_status_t` is a plain enum (pending / success / error) with no message payload: a single message was useless next to the full diagnostic list, so all details come from diagnostics.
- **Pass list C API** (step 11): `mewo_project_add_pass(project, name, source, &id)`, `mewo_project_remove_pass(project, id)`, `mewo_project_move_pass(project, id, new_index)` (`new_index` = the pass's index after the move; same index succeeds as a no-op). Removing the last pass returns **`MEWO_ERROR_INVALID_OPERATION`** (-4, "valid arguments, but not allowed in the current state"), distinct from `INVALID_ARGUMENT` for unknown IDs/indices, so hosts can tell "you named nothing" from "you can't do that now". Sessions catch up on structure changes at their next render (reconcile drops states, discarding their tickets, and creates states that compile via the normal staleness check), so status/diagnostic queries reflect the pass list as of the last render.
- **SDL host folder mode:** `mewo_sdl [<folder>]`; every `*.wgsl` in the folder except `common.wgsl` is a pass, ordered by file name (`01_scene.wgsl`, `02_blur.wgsl`, ...), and `common.wgsl` is the Common source (deleting it clears Common). Example chain in `hosts/sdl/shaders/`. The folder is rescanned every 250 ms; sources are polled every frame. A sync adds new passes **before** removing old ones (a rename never empties the project), then `move_pass`es each to its file's index front to back. The project's initial pass is removed after the first sync. There's deliberately no protection against deleting the last pass file (it's a dev host): the removal just fails with `INVALID_OPERATION` and the host logs it. Without a folder, the host renders the default project.
- **Where inputs are validated** ("parse, don't validate"):
  - The C API layer (`src/*.cpp`) checks the *C representation*: required pointers → `assert`; enum values that are `NONE`/out of range (a C enum can hold any `int`) and tagged unions missing their data (e.g. null `layer`/`hwnd`) → `MEWO_ERROR_INVALID_ARGUMENT`. It converts C input into C++ types where those states are unrepresentable (e.g. `SurfaceSource` is a `std::variant` with no "none"), via named conversion helpers (e.g. `to_surface_source`) in the file's unnamed namespace.
  - The core checks *domain rules* that would be wrong from any caller (tests, other frontends) inside the owning function (e.g. `create()`), signalling failure through its return type (see error handling above; add an error type once a domain rule needs its own public code).
  - Every C API function has the same shape: assert pointers → convert (invalid → `INVALID_ARGUMENT`) → `try { core call }` → map errors.
  - Zero **surface** sizes are valid, not an error: the core skips configuring/presenting at 0×0. Note SDL3 never reports 0×0 on minimize (Cocoa and Win32 both send `SDL_EVENT_WINDOW_MINIMIZED` and keep the last size); 0×0 comes from other hosts (a collapsed SwiftUI view, a hidden canvas). A host that wants to avoid hidden GPU work can stop calling `mewo_session_render` while minimized (keep ticking the runtime) and resume on `SDL_EVENT_WINDOW_RESTORED`; the SDL reference host deliberately doesn't, since it's a test app. Zero **render** sizes are invalid (`INVALID_ARGUMENT`); the host keeps the last size instead.
- Threading: all calls for a runtime happen on one thread; libmewo does no locking (for now).
- File I/O: libmewo never touches the filesystem. The core owns the project format (parsing/serializing); the host moves the bytes (provides referenced files, writes serialized output, watches files for hot reload).

### Pass model
Simplified for v1 (decided in step 3): a linear chain. The richer graph model is kept under "Future goals" below.
- A project is an **ordered list of passes**; execution order = list order. Each pass reads the output of the **pass before it** (as `prev`), plus any **external sources** (image textures, keyboard, later video/audio). Passes can't read other passes, their own previous frame, or later passes. Why: post-processing chains (e.g. blur, bloom, tonemap) are the main multi-pass use, a straight chain covers them, and it removes graph validation, cycles, and feedback state from v1.
- **A project always has at least one pass.** A new project starts with one pass; removing the only pass fails. There is no output flag, no `main_pass` flag, and no special Image pass: the **last pass in the list is what gets presented/exported**, and "pre / main / post" grouping, if any, is a UI concept.
- **The blit is not a pass.** Presentation is an internal session step that always runs after the last pass and copies its texture to the surface (or is replaced by readback for export). It never appears in the project's pass list, IDs, validation, or saved file. Why: it depends on the surface format and only runs when presenting, so it isn't part of the document; putting it in the list would need special cases in every pass API (count, IDs, move, remove, validation, serialization).
- **The first pass reads black as `prev`.** Every pass always has the `prev` input, so a shader stays valid wherever it sits in the list and reordering never breaks compilation. Reading black there is not reported as a problem.
- **All pass textures have the session's render size and one fixed internal format, `rgba16float`.** Why: one size makes `mw.resolution` and mouse coordinates the same for every pass; `rgba16float` avoids banding in post chains, and is renderable and filterable on every WebGPU device including the web. Still display-referred (no automatic gamma); the blit converts to the surface format.
- **The session ping-pongs two textures for the whole chain** (pass `i` writes `i % 2`, reads `(i + 1) % 2`; pass 0 reads B), regardless of pass count, because each output is only read by the next pass. **B is cleared to black at the start of every frame**, and that is the first pass's `prev` (no separate black texture). Why: `prev` is then render-sized in every pass, so `textureDimensions`/`textureLoad` behave the same wherever a pass sits (a 1×1 black texture would make pass 0 read out of bounds), and it needs one fewer texture and bind group; the cost is one clear per frame. Always clear, even with one pass, since B may hold stale output after passes are removed. The blit reads the last pass's target (the `prev` of an imaginary pass `n`). Render size changes reallocate just those two textures and their bind groups. Bind groups: group 0 per-frame uniforms, group 1 `prev` (two shared bind groups), group 2 the pass's assets (later).
- **Invalid states are allowed but reported.** Why: editors need transient invalid states. The project exposes validation results (no GPU needed); the UI highlights problems; the session binds a **black fallback texture** for broken external inputs (a visible signal) and reports a warning diagnostic.
- Sampling (filter/wrap) is per external input binding; `prev` uses a fixed sampler (linear, clamp to edge).
- **Pass IDs** are stable opaque integers from the core, never list indices. Each `Project` assigns them from its own counter starting at 1 (`next_pass_id_++`); an ID never changes for a pass's lifetime (renames, edits, and reorders keep it) and is never reused within a project, even after the pass is removed. IDs are per project, so two projects can both have pass 1. **`0` means "no pass"** (`MEWO_PASS_ID_NONE` at the C boundary; inside the core, use `std::optional<Pass::Id>`). Why: C hosts zero-initialize structs (`= {0}`, `calloc`), so an unset field reads as "none" instead of silently naming a real pass; never reusing IDs means a stale ID (in the session's map, an in-flight compile, or a host) can't alias a newer pass.
- Common code is a project-level shared source prepended to every pass, not a pass.
- **Named external inputs:** each external input has a user-chosen name used directly in WGSL (e.g. `noise`). Names default to `in_0`, `in_1`, ... (the UI shows inputs as an ordered list so the numbering reads clearly). Smart defaults derived from the source were considered "too magic" for now; if added, name once at creation and never auto-rename. Names must be valid, unique WGSL identifiers that don't collide with keywords, `prev`, or the reserved `mw` / `mw_*` names. Why: readability.

#### Future goals (not v1)
- **Feedback:** a pass reading its own output from the previous frame (trails, game of life, simulations, accumulation). Fits in as one more source kind; only that pass needs a second texture. Brings back: an explicit session `reset` that clears buffers and the clock, buffer contents surviving source edits (the pipeline swaps, the textures stay), and possibly preserving contents across reallocation or a "reset on compile" option.
- **Reading any pass, not just the previous one:** inputs bound to a pass plus an explicit frame, `current` (only valid from earlier passes, so no cycles) or `previous` (any pass, including itself). Reordering then never silently changes meaning, and double buffering is inferred from which passes are read as `previous`. "Previous pass in list" would stay as a source kind.
- **Per-pass size and format** (match session / scale / fixed; rgba8 / rgba16f / rgba32f). Makes `mw.resolution` and mouse space per pass again.
- **Choosing which pass is presented**, if non-last passes ever need to be shown (e.g. debugging a mid-chain pass).

### Shader contract
- The contract (entry point, built-ins, input bindings, coordinate conventions) is an API: projects store a **contract version**.
- **WGSL is the only shader language** (browsers only accept WGSL). Shadertoy compatibility is not a goal.
- **Entry point:** the user writes `fn main(fragCoord: vec2f) -> vec4f`. The core owns the vertex shader (fullscreen triangle) and generates the real `@fragment` entry point, which calls the user's `main`. **Reserved names: `mw` and everything starting with `mw_`** (types, variables, functions, e.g. `mw_Uniforms`, `mw_uniforms`); every generated identifier uses them, and user code must never declare them. Why: it matches the user-facing `mw` struct, so mewo occupies one namespace in WGSL instead of two (`mw` and `mewo_`).
- **Inputs in WGSL:** the previous pass is always `prev_tex` / `prev_smp`; an external input named `noise` is exposed as `noise_tex` (texture) and `noise_smp` (sampler). Why: WGSL forbids textures/samplers in structs, so a `bloom.handle`-style struct is impossible; both suffixes abbreviated for consistency. The bare name stays free for user variables, e.g. `let prev = textureSample(prev_tex, prev_smp, uv);`. Since all passes share one size, `textureLoad(prev_tex, vec2i(fragCoord), 0)` is an exact per-pixel read.
- **`mw` fields (v1):** `resolution: vec2f` (the session's render size, shared by all passes), `time: f32` (seconds), `delta_time: f32`, `frame_number: u32`, `frame_rate: u32` (frames per second, rounded to the nearest integer), `mouse: { position: vec2f, click: vec2f, down: bool }`. Mouse is always tracked (including hover), in render-size pixels, y-up (stored normalized in the uniform buffer, scaled in generated init). `date` dropped (the core can't read OS clocks; hurts deterministic export). Start minimal: adding fields later is non-breaking, removing is breaking. Possible later: `mouse.buttons`, `mouse.pressed`, `mouse.inside`.
- **Time precision:** WGSL has no `f64`/`u64`/`i64`, so shader-side time stays `f32` seconds (step size ~4 ms at 10 h, ~8 ms at a day; fine for v1). The CPU-side clock is kept as an exact 64-bit integer tick count (or double) and converted to `f32` each frame, so there's no accumulated drift. A precision-friendly split (`u32` whole seconds + `f32` fraction) can be added later if needed.
- **Built-ins are a namespaced struct named `mw` (e.g. `mw.time`, `mw.mouse.down`), not Shadertoy's `iTime`-style globals.** Why: compatibility with Shadertoy isn't a main goal (porting needs work anyway), so there's no reason to carry its baggage (e.g. `vec3` `iResolution`, `iMouse` sign-encoding). Planned approach: the user-facing struct is a `var<private>` filled by generated init code from the underlying uniform buffers (group 0 per-frame, group 1 per-pass), so its layout can be friendly (nested structs, bools) independent of the buffer layout.
- **Shader output is display-referred:** mewo applies no automatic gamma/sRGB encoding anywhere (non-sRGB surface formats, pass textures stored as-is). Shaders that want linear-light math apply gamma themselves, as on Shadertoy.
- **Coordinates are y-up everywhere** (origin bottom-left, like Shadertoy). Internal textures are stored with row 0 = bottom, so `@builtin(position).xy` is already the y-up coordinate and sampling needs no flips. Flip only at presentation to the surface, readback/export, and image asset upload.
- **WGSL extensions/directives (e.g. `f16`) are a project-level setting** that the core emits at the top of the assembled module. Users don't write `enable` directives. Why: directives must precede declarations, and the core can check device support first.
- Module assembly order: user pass source first (so its line numbers need no mapping, since WGSL module-scope declarations are order-independent), then Common source, then generated prelude + entry point. A segment map translates diagnostics (Common lines, collisions with generated names).
- Uniform layout has a single source of truth in C++ (a field table) that generates both the WGSL declarations and the byte offsets.

### Repo & build
- Layout (repo root): `include/mewo/mewo.h` = the public C header hosts include; it includes `include/mewo/detail/*.h`, which split it up for internal organization only (hosts don't include them directly). Every `detail/` header must be included from `mewo.h` so `mewo_c_check` compiles it and clangd can find its flags, and starts with `// IWYU pragma: private, include <mewo/mewo.h>` so clangd's auto-include inserts `<mewo/mewo.h>` instead of the detail header (the `.clangd` `IgnoreHeader` only silences unused-include warnings, it doesn't stop insertion). `src/` (with its own `CMakeLists.txt`) holds the library: the **C API layer** is `src/<object>.cpp` at the top level (`runtime.cpp`, `surface.cpp`, `version.cpp`; only `extern "C"` functions); `src/impl/<object>.{hpp,cpp}` holds the core object `mewo::impl::<Object>` (`impl::Runtime`, `impl::Surface`, later `impl::Session`, `impl::Project`) **and** its global C handle struct (`struct mewo_runtime { std::unique_ptr<mewo::impl::Runtime> impl; ... };`, defined at global scope because the C header declares it there), with per-object helpers in `src/impl/<object>/` (e.g. `impl/surface/source.hpp`); `src/core/` holds shared internals (`event.*` internal events, `pass.*` (`mewo::Pass`, GPU-free model data shared by `Project` and `Session`), `gpu/` = `MoveOnlyHandle` + the `mewo::gpu::*` handle aliases and WebGPU string conversion, `utility/match.hpp`). Tests live in a top-level `tests/` with their own `CMakeLists.txt` (`mewo_tests`, `mewo_c_check`). Also `hosts/` (`sdl/` reference host in plain C, later `macos/`, `web/`; "hosts" because the web isn't really an app), `third_party/`, `cmake/` (`webgpu.cmake` selects the implementation; `utils.cmake` has `mewo_set_target_defaults(target C|CXX)`, which sets the language standard (C11 / C++23, no extensions) and the warning flags). Every first-party target calls `mewo_set_target_defaults`. In CMake, use `${CMAKE_CURRENT_SOURCE_DIR}` / `${PROJECT_SOURCE_DIR}` for include paths, never bare relative paths or `..`.
- **CMake targets:** `mewo` (the whole library, one target; links the JSON lib, webgpu, stb), `mewo_sdl` (links `mewo` + SDL3; only hosts see SDL), and with tests on `mewo_tests` (links `mewo`, white-box: includes `src/` headers directly) and `mewo_c_check`. There is **no separate `mewo_model` target** anymore (dropped during step 2): the project/shader model code staying GPU-free (never including webgpu) is a convention checked in review, not enforced by the build. Why: one target is simpler, and the split forced awkward placement questions (e.g. where `Error` lives); the cost is that tests now need Dawn built, which is a one-time cost per build directory.
- The top-level `src/*.cpp` files are the only place C functions meet C++ (thin `extern "C"` + try/catch forwarding). WebGPU-implementation-specific code (surface sources, extensions) stays inside the `impl/` files that need it.
- `tests/c_check.c` (target `mewo_c_check`, an OBJECT library) compiles `mewo.h` as C11 `-pedantic` to catch C++-isms. It must stay C11, not C23: C23 makes `f()` mean `f(void)` and makes `bool` a keyword, which would hide exactly the mistakes it exists to catch.
- **Presets** (`CMakePresets.json`): configure `debug-clang` / `release-clang` (Ninja, clang/clang++, `build/<preset>`, compile_commands on). Build presets per configuration: `<cfg>` (everything), `<cfg>-tests` (`mewo_tests` + `mewo_c_check`), `<cfg>-host-sdl` (`mewo_sdl`). Test presets per configuration with `outputOnFailure` and `noTestsAction: error`. The user drives builds through VS Code's CMake Tools extension ("CMake: Select Build Preset"; "[Targets In Preset]" is the target setting, not the preset).
- **Gotchas found during setup:** Dawn registers `tint_unittests` with CTest unless `TINT_BUILD_TESTS` is OFF. After adding any `set(... CACHE ...)` dependency option to an existing build dir, reconfigure with `cmake --preset <p> --fresh`, because non-`FORCE` cache sets don't override cached values. Multi-line generator expressions break (whitespace splits or leaks into flags); use one-line `"$<...:a;b>"` forms. Catch2 only requires C++14, which is clang's default for the MSVC ABI, so its compiled library lacked `StringMaker<std::string_view>` (comparing `string_view`s in `CHECK` failed to link); `third_party/CMakeLists.txt` builds Catch2 as C++23, and its autodetection then enables `string_view` support (no forced `CATCH_CONFIG_*` option needed).
- **Dawn first** as the `webgpu.h` implementation, selected through `cmake/webgpu.cmake` so wgpu-native can be added later.
- **Dependencies are git submodules only** (no FetchContent). Small single-header deps (stb_image) are vendored in `third_party/`. Note: Dawn's own build may still fetch its dependencies via its script (`DAWN_FETCH_DEPENDENCIES`).
- **Tests use Catch2 v3** (submodule, registered with CTest via `catch_discover_tests`). Why: expression-decomposing `REQUIRE`, and `SECTION`s suit the many small variations in GPU-free project/shader model tests; v3 is a compiled library, so no single-header compile cost.
- The macOS SwiftUI app will be an Xcode/SwiftPM project linking a libmewo static lib/xcframework, not built by CMake.
